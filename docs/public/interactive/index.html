全局：这个仓库是什么

01

定位与开源边界

先弄清楚这个仓库是完整服务里的哪一块，读代码时才知道哪些「空函数」是故意留空的。

DeepSeek 的线上推理是 E/P/D 分离（Vision Encoder / Prefill / Decode 三类实例分开部署）的集群系统。DeepInfer 开源的是其中单个推理引擎内部的全部逻辑：调度、模型执行、采样、并行通信和 kernel。负载均衡器、KV cache 存储（3FS）和 P→D 迁移与内部基础设施耦合，没有开源。

开源 引擎内能读到的

  • C++ 调度器、块管理器、MTP 变长验证调度
  • V4.1 模型（mHC、稀疏注意力、Engram、YoCo、MoE、ViT）
  • 采样器、DSpark 草稿模型、结构化输出
  • DP/EP/CP 通信、EPLB、CUDA Graph
  • ~30 个 TileLang 自定义 kernel（CUDA + 昇腾两套）

留空 读到会是「虚函数」的

  • PD 分离：init_pd_split、send_processed_prompts
  • KV 落盘：do_save_kvcache、pe_do_save_kvcache
  • 跨请求前缀命中：hit_tokens 由外部注入
  • 在线服务封装（只有离线 LLM 类）
llm_engine.py:800–858
和 vLLM 的关系：DeepInfer 最初主要基于 vLLM 构建（文件头仍写着 Derived from vLLM），对外 API（LLM、SamplingParams、LLMEngine.step）和 vLLM 很像；但热路径几乎都换成了 C++（调度、输入元数据准备）和 TileLang/DeepGEMM/FlashMLA kernel，并且只服务一个模型家族。第二部分会先把 vLLM 讲清楚，第三部分再逐项对比。

03

进程模型与启动

搞清楚「几个进程、谁和谁通信」，后面的并行代码才看得懂。

GPU 被切成若干个 DP rank（data parallel，数据并行副本），每个 DP rank 是一个独立进程，里面有一个完整的 LLMEngine：自己的调度器、自己的 KV cache、自己的一批请求。如果开了 CP（context parallel），一个 DP rank 再占 cp 张卡：0 号卡是 driver worker，跑在引擎进程里；其余卡各起一个 follower 进程，死循环等 driver 广播要执行的方法名。

引擎初始化顺序

  1. _init_workers：起 CP follower 进程，构造 driver Worker；Worker 里绑 NUMA/CPU、建进程组。llm_engine.py:368
  2. load_model：先初始化 Engram 的压缩词表，再加载权重。base.py:203
  3. profile_num_available_blocks：跑一次最大 batch 的 dummy forward 测峰值显存，剩余显存 × gpu_memory_utilization 减去 state cache 后除以每块字节数，所有 rank 取平均。vLLM 的 determine_available_memory 也是同一套「先 profile 再把剩下的都给 KV」的思路。base.py:212
  4. init_cache_engine 分配 KV；warm_up_model 捕获 decode CUDA Graph，并在开启变长验证时实测每个 graph 尺寸的耗时，得到 decode_perf_curve。base.py:274
  5. 最后才构造 C++ BlockManager 和 Scheduler，因为它们需要上一步算出的块数。llm_engine.py:265
Part 2

推理基础：先看懂常规做法

不了解基线就看不出优化。这一部分不讲 DeepInfer 代码，只讲 LLM 推理的基本事实和 vLLM 的标准答案。

04

推理到底在算什么

所有推理框架都在优化同一个循环。先把这个循环画出来。

大模型是自回归生成的：每次 forward 只产出下一个 token，把它接到输入末尾，再 forward 一次。一个请求的生命周期分成两个阶段，它们的计算特性完全不同：

术语表（后文会反复出现）

token
模型处理的最小单位，中文大约 1–2 个字一个 token。
forward / step
模型跑一次前向计算。框架里「一步」= 调度 + 一次 forward + 采样 + 后处理。
prefill / decode
处理输入 prompt / 逐个生成输出 token 的两个阶段。
TTFT / TPOT
首 token 延迟 / 每个输出 token 的间隔。前者看 prefill，后者看 decode。
吞吐 throughput
每秒每卡产出多少 token，决定成本。和延迟互相拉扯：batch 越大吞吐越高，但每个请求变慢。
batch
一次 forward 里同时处理的请求（或 token）集合。
KV cache
注意力层为已处理 token 缓存的 Key/Value 向量，避免每步重算历史，见第 06 节。
kernel
在 GPU 上执行的一个函数（一次矩阵乘、一次注意力…）。CPU 每发射一个 kernel 有几微秒开销。
CUDA Graph
把一串 kernel 录下来、之后一次性重放，省掉逐个发射的 CPU 开销。
MoE
Mixture of Experts：FFN 换成很多个「专家」，每个 token 只激活其中几个。参数多、单 token 计算少。
TP / DP / EP / CP
张量并行（切矩阵）/ 数据并行（复制整份，各跑各的请求）/ 专家并行（把专家分到不同卡）/ 上下文并行（把一条长序列切到多卡）。见第 16 节。
FP8 / FP4
8 位、4 位浮点格式。比 BF16 少读一半或四分之三的字节，配合 scale（缩放因子）保持精度。
05

瓶颈：显存带宽（可交互）

这是全篇最重要的一节。DeepInfer 的几乎每一项优化，都能用这里的一个公式解释。

GPU 一步 decode 的耗时，大致取决于两件事里更慢的那个：把数据从显存搬到计算单元的时间，和真正做乘加的时间。

一步耗时 ≈ max( 读权重 + 读 KV  ÷ 显存带宽 ,  2 × 参数量 × 本步 token 数 ÷ 峰值算力 )

以 SM100（B200 级）为例：显存带宽约 8 TB/s，FP8 稠密算力约 4.5 PFLOPS（DeepInfer 自己记的 BF16 峰值是 2250 TFLOPS，FP8 取 2 倍，见 device.py:151）。下面用一个 70B 稠密、FP8 权重的玩具模型感受量级，拖动参数看看：

06

KV cache 与 PagedAttention

KV cache 是推理框架管理的最重要的资源，也是 vLLM 成名的原因。

KV cache 是什么

注意力层里，每个 token 会算出一个 Query、一个 Key、一个 Value。生成第 t 个 token 时，它的 Query 要和前面所有 token 的 Key 做点积、再对 Value 加权求和。前面 token 的 K、V 不会变，所以第一次算完就存起来，后面每步直接读：这就是 KV cache。代价是它占显存，并且随上下文线性增长：

每 token KV 字节 = 层数 × KV 头数 × 每头维度 × 2（K 和 V）× 每元素字节
Llama-3.1-70B（GQA，BF16）= 80 × 8 × 128 × 2 × 2 B = 320 KB / token  →  32K 上下文 ≈ 10 GB / 请求

显存能装下多少请求的 KV，直接决定了 batch 能开多大，也就决定了上一节的吞吐上限。

vLLM 的解法：PagedAttention

早期框架给每个请求按「最大可能长度」预留一整段连续显存，但大多数请求根本用不满，浪费严重，还有碎片。vLLM（2023，SOSP 论文）借鉴操作系统的虚拟内存分页：把 KV 切成固定大小的块（vLLM 默认 16 token 一块），每个请求用一张块表把逻辑块映射到任意位置的物理块，按需分配。

07

vLLM 是怎么设计的

vLLM 是目前最常用的开源推理框架，也是 DeepInfer 的出发点。理解它的设计取舍，才能看懂 DeepInfer 为什么改。

① 连续批处理：每一步都可以换人

最朴素的做法是「静态批」：凑够一批请求一起跑，等最长的那个结束才放下一批进来。短请求早早结束后，它的位置一直空着。Orca（OSDI 2022）提出迭代级调度：每一步 forward 之后都重新调度，结束的请求立刻腾出位置，新请求下一步就能加入。vLLM 把它和 PagedAttention 结合起来，成为今天所有框架的标配。

④ 通用框架 vs 专用框架：一张总对比

09

调度器

直觉调度器每步回答三个问题：跑哪些请求？每个请求算几个 token？显存不够时牺牲谁？答案决定了 batch 的形状，也就决定了第 05 节公式里的「本步 token 数」。
vLLMPython 统一调度器：一个 token 预算，decode 先占，剩下的给 prefill 块。同一步里 prefill 和 decode 混在一起。
DeepInferC++ 调度器：一步要么全 prefill、要么全 decode，由整个 DP 组投票决定；decode 步的每请求 token 数由投机解码的置信度决定。

为什么不混批？

混批在单机、小模型上是最优解，但 DeepInfer 的场景有三个约束：

  1. EP 要求全组步调一致。64 个 DP rank 在每个 MoE 层都要做 all-to-all。如果 rank 0 这步在做 30K token 的 prefill、rank 1 只做 64 个 token 的 decode，rank 1 每层都要等 rank 0，decode 延迟被 prefill 拖垮。
  2. decode 步要能整图捕获。纯 decode 步的形状只由「总 token 数」决定，可以预先录好 CUDA Graph；混了 prefill 就只能 eager 或分段图。
  3. 线上本来就是 PD 分离。Prefill 和 decode 跑在不同实例上（第 01 节），NORMAL 引擎的「交替」只是离线/小规模部署时的折中。

decode：块不够就抢占

decode 时先把 running 按输出长度降序排，从输出最短的一端开始分配新块，块不够时从另一端抢占（_preempt）。被抢占的请求要么回到 waiting 重算，要么在 stop_preempted_request=True（EngineArgs 默认）时直接结束；离线 LLM 把它改成了 False。vLLM V1 的抢占也是「释放块、之后重算」，不再像 V0 那样换出到 CPU。scheduler.hpp:622

CPU 开销：异步调度与 CUDA Graph

直觉GPU 一步 decode 只要几毫秒。如果 CPU 每步要花 1–2 ms 调度、准备输入、逐个发射几千个 kernel、再处理输出，GPU 有相当一部分时间在等 CPU。这是第 05 节的杠杆 ⑤。
vLLMCUDA Graph（默认整图 + 分段图）消掉 kernel 发射开销；--async-scheduling 让 CPU 提前一步调度；Model Runner V2 把输入准备也搬到 GPU。
DeepInfer调度与输入准备用 C++；decode 整图捕获；ZOS（零开销调度）把第 N 步的后处理藏到第 N+1 步 forward 后面，长度修正在 GPU 上做，整条路径禁止 CPU-GPU 同步。

CUDA Graph：把几千次发射变成一次

一个 40 层 MoE 模型的一步 decode 由几千个 kernel 组成，每个 kernel 从 CPU 发射要几微秒，加起来可能和 GPU 计算时间相当。CUDA Graph 先把整串 kernel「录」下来，之后每步只需一次重放。限制是录下来的形状固定，所以要按 batch 大小分桶，各录一张图。

vLLM 为什么要分段图

混合 batch 里有长短不一的 prefill，注意力的形状每步都在变，很多注意力后端不能整图捕获。于是 vLLM 用 torch.compile 在注意力处把模型「切开」，注意力以外的部分录成图，注意力 eager 执行。纯 decode batch 再额外用整图（FULL_AND_PIECEWISE）。

DeepInfer 只录 decode，整图

因为一步只做一种（第 09 节），decode 步的形状只取决于总 token 数，注意力也能一起录。按 build_graph_batch_sizes 分桶：1、2、4，然后每 8 一档；实际 token 数向上取到最近的桶，用 padding 序列补齐。prefill 计算量大、发射开销占比小，直接 eager。cuda_graph_runner.py:41

异步调度：让 CPU 和 GPU 同时干活

串行流程是 schedule(N) → forward(N) → sample(N) → 同步 → post_process(N)，GPU 在后处理和下一步调度期间空闲。ZOS 把第 N 步的后处理推迟到第 N+1 步 forward 发射之后做，CPU 工作被藏进 GPU 计算里。NORMAL/COMPLETION 引擎默认开启。arg_utils.py:48

难点：CPU 看到的状态晚一步

没有投机解码时，异步调度相对简单：每个请求每步固定多 1 个 token，下一步的长度可以提前算好。开了投机解码就麻烦了：调度第 N+1 步时，第 N 步还没验证完，CPU 不知道每个请求接受了几个草稿，也就不知道 KV 长度、下一步从哪个位置开始。vLLM 社区也提到这个组合在 V1 里很难做干净。DeepInfer 的做法：

  • CPU 按「乐观假设」准备好 seqlen_q/seqlen_k，再由 C++ 的 prepare_zos_inputs 算出本步和上一步 batch 的对应关系 remap。zos.cpp
  • 在 GPU 上用上一步真实的接受数和置信度修正长度：compute_seqlens_k_zos、compute_seqlens_q_by_confidence_rates（两个 TileLang kernel）。worker.py:191
  • 上一步刚采出来的 token 直接在 GPU 上从 prev_sampled_token_ids 取，不回 CPU。zos_status.py:24

整条路径上的 execute_main_model/execute_sample 都包在 forbid_cuda_sync() 里：一旦有人写了隐式同步（比如 .item()），直接报错。tests/test_cuda_sync_guards.py 专门测这个。

V4.1-Flash 模型结构

直觉推理框架是围着模型结构写的。V4.1 不是标准 Transformer：KV 有好几种、层与层之间共享 KV、残差流有 4 条、还有查表模块。这些结构决定了引擎里一半的特殊逻辑。

MoE 为什么适合推理

384 个专家里每个 token 只用 6 个 + 1 个共享专家：总参数很大（知识多），单 token 计算量小。但第 05 节说过 decode 是 memory-bound：batch 一大，几乎所有专家都会被某个 token 选中，每步还是要把全部专家权重读一遍。所以 MoE 推理的关键是把专家分散到很多卡上（第 16 节）。

实现上：权重 FP4、激活 FP8；EP 组在一个 NVLink 域内时走 DeepGEMM 的融合 Mega MoE，否则走 DeepEP dispatch/combine。mlp.py:184

Engram：用查表换计算

挂在 layer 1 和 14：把 token 映射到压缩词表（99,092），取 2–4 阶 n-gram 的哈希，从约 3.8 亿行的表里查 embedding，门控加进残差。查表几乎不耗算力，但表很大，所以默认放在 CPU 内存，按 hash 跨 rank 分片取回。engram.py:127

引擎侧的连锁影响：C++ 调度器也要维护一份「压缩词表下的 token 序列」，新生成的 token 要同时追加到两份序列里（map_engram）。

注意力与 KV 存储

直觉KV cache 同时决定两件事：能装下多少并发请求（batch 上限），以及每步要读多少字节（第 05 节的 KV 项）。长上下文时它是头号瓶颈。
vLLM对标准模型：每层一份分页 KV，块大小 16 token，可选 FP8 KV；对 MLA、滑窗等结构由各自的 attention backend 和混合 KV 管理器适配。
DeepInfer模型本身就把 KV 压得极小：单头 latent + 2 倍压缩 + 40 层只有 4 层存块 KV + FP4。引擎相应地有两套分配器和 5 种 KV 张量。

每 token 要存多少 KV：一代比一代小

四代压缩分别靠什么：

  1. GQA：多个 query 头共用一组 KV 头（64 → 8）。
  2. MLA（DeepSeek-V2/V3）：所有头共用一个 512 维的潜变量（latent），计算时再「展开」。KV 只有 1 个头。
  3. V4.1 的压缩 KV：C2 层把相邻 2 个 token 的 KV 压成 1 条；再加跨层共享：40 层里只有 layer 2、8、14、20 真正存 KV，其余层复用最近的 source 层。
  4. 低精度：主 KV 用 FP4（per-16 e4m3 scale），比 BF16 再小 4 倍。

只看一部分 KV：滑窗 + 稀疏检索

存得少还不够，每步读的也要少。标准注意力每个 query 要读完整的上下文；V4.1 每个 query 只看「最近 128 个 token」加「indexer 挑出来的 512 条压缩 KV」，读取量与上下文长度基本无关：

KV 跨层共享的代码

kv_source_layer_ids=[2,8,14,20]：每一层复用「不晚于自己的最近一个 source 层」的 ca_cache，所以 layer 2–7 共用 layer 2 的，layer 20–39 全部共用 layer 20 的。indexer 模块同理，source 是 [2,8,14,20,24,28,32,36]。映射函数只有三行：config.py:62 _source_map；复用别层 KV 的层不占新显存：cache_engine.py:165。每层自己的 SWA KV 则逐层独立。

前缀缓存、YoCo 与有界重放

直觉多轮对话和 Agent 的输入大部分是上一轮重复的。如果之前算过的 KV 还在，就只需要 prefill 新增部分：prefill 成本可能降一个数量级。剩下的问题是：KV 能留多久、在哪、缺一部分怎么办。
vLLMGPU 显存里的哈希块缓存，LRU 淘汰；外部存储需要接 KV connector（如 LMCache）。命中多少就复用多少。
DeepInfer块 KV 存外部 3FS（保留 3–7 天），引擎只接收「命中长度」；滑窗 KV 缺失时只重放最后 128 token。再加上 YoCo：后 20 层 prefill 只算末尾 140 个 token。

滑窗 KV 带来的新问题

分页的块 KV 很容易缓存：按块哈希、按块存取。但 V4.1 每层还有一份滑窗 KV，它是「最近 128 个位置」的状态，不按块对齐，没法和块 KV 一起分页共享。文档里的规则：块 KV 决定命中长度，滑窗 KV 只决定最后一块要不要重算。滑窗 KV 缺失时，只重放命中前缀的最后 128 个 token，把注意力窗口截在重放段内，得到一个近似的滑窗状态，成本是常数，和上下文长度无关。

YoCo：后半个模型只看末尾

第一个 C1 层（layer 20）之前的层叫 prefill 侧，之后的叫 YoCo consumer（文档里叫 CED 架构的 decoder 层）。consumer 层的压缩 KV 全部来自 layer 20 入口的 hidden（第 12 节的跨层共享），它们自己只需要逐层算 SWA KV。开启截断后，consumer 层在 prefill 时只对末尾 140 个 token 算 query：

mask 模式保留全部 query、只收窄 SWA 可见范围，计算量不变，用来验证和 compact 在数值上等价（examples/yoco/）。截断的元数据准备见 input_metadata/yoco.py:94。vLLM 里没有对应机制，因为这依赖 V4.1 的层间 KV 共享结构。

DSpark 投机解码

直觉第 05 节说过：decode 时 GPU 主要在搬权重，多算几个 token 几乎不加时间。那就先用一个便宜的小模型「猜」后面 5 个 token，再让大模型一步把它们全部检查一遍，猜对几个就一次前进几个。
vLLM支持 ngram、EAGLE/EAGLE3、MTP、草稿模型等；每步固定验证 num_speculative_tokens 个；EAGLE 类草稿逐个自回归生成。
DeepInfer3 层草稿模型一次 forward 并行出 5 个草稿，另带置信度头；调度器按置信度给每个请求分配不同的验证长度。

基本流程：猜 → 验 → 接受前缀

草稿怎么来：逐个猜 vs 一次猜 5 个

  • 代码里叫 DFlash，配置字段叫 dspark_*。3 个草稿层，复用主模型的 embedding 和 lm_head，自带 128 专家 top-3 的小 MoE。dflash.py:82
  • 输入特征来自主模型 layer 37/38/39 的 attention 输入（对 4 条残差流取均值），在主模型 forward 里顺手写进草稿层的 KV。
  • 块长取 DEEPINFER_USE_NEXTN_DECODE（默认 5），与层数 3 无关；5 个位置的 hidden 一次得到，再逐位置采样（可选 Markov 头让前一个草稿影响后一个）。dflash.py:230
  • 每个草稿还有一个置信度头：sigmoid(w·[h ⊕ markov_emb] / T)，预测它被接受的概率。

验证多少：按边际收益挑草稿（可交互）

固定验证 5 个有浪费：有的请求在写代码，草稿基本都对；有的在写诗，第 2 个就错了，后面的验证算力白花。DSpark 的思路：草稿 j 被接受的前提是前面都被接受，所以位置接受率是置信度的累乘。调度器把所有请求所有位置的累乘值降序排，一个个加入验证集合，用实测的「graph 尺寸 → 耗时」曲线估算吞吐 = 期望接受数 ÷ 预计耗时，取最大值。mtp_varlen.hpp:150

官方文档给的生产数据：变长验证让每步平均验证长度从 5 降到 3.2–4.4，平均接受长度基本不变（3.29 → 3.20），在每卡约 60 并发时吞吐提升约 5%，并发越高收益越大（96 并发 +11%）。这符合第 05 节的直觉：并发越高，GPU 越接近算力瓶颈，「多验证几个几乎免费」就越不成立，省下的验证算力越值钱。

接受判定：拒绝采样

置信度只决定「验证几个」，不参与「接不接受」。它即使估错了也只影响性能，不影响正确性。

采样、确定性、结构化输出

直觉模型每步输出词表上 12.9 万个分数（logits），采样就是按温度、top-p、top-k 把它变成概率再抽一个 token。看似简单，但有两个工程难题：同样的输入为什么结果会变？怎么强制输出合法 JSON？
vLLM采样器参数更全（含 min-p、各种 penalty、logits processor）；结构化输出用 xgrammar / guidance 生成 token bitmask。
DeepInfer参数精简到线上需要的；无状态随机数 + batch-invariant 模式实现逐位可复现；结构化输出同样用 xgrammar，但异步编译并与投机解码逐草稿配合。

为什么同样的输入会得到不同的输出

浮点加法不满足结合律：(a+b)+c 和 a+(b+c) 的结果可能差最后一位。GPU kernel 为了快，会根据 batch 大小选不同的切分方式和归约顺序。于是同一个请求，和不同的其他请求拼在一起时，算出的 logits 有微小差异，采样时偶尔就会选到不同的 token，之后整段输出都不一样。2025 年 Thinking Machines 的文章让这个问题广为人知。

batch-invariant 推理

DEEPINFER_BATCH_INVARIANT=1 把 DeepGEMM、注意力、通信切到「结果与 batch 组成无关」的算法（仅 NVIDIA），代价是一点性能。离线示例在 NVIDIA 上默认打开。runtime_config.py:63

确定性采样

随机数不来自全局 RNG，而是 SplitMix64(seed + f(3·pos + case))：case 0/1/2 分别是普通采样、残差重采样、接受判定。同一序列同一位置永远拿到同一个随机数，与 batch 里还有谁无关。要复现必须显式传 seq_seed（默认随机），并关掉变长验证。

采样器参数

  • 支持：temperature、top-p、top-k、top_logprobs、token 黑名单、first_n_token_no_eos。没有 min-p 和 repetition/frequency/presence penalty。sampling_params.py
  • 温度 0 被钳到 1e-5，没有单独的 argmax 分支。
  • top-p/top-k 用直方图找阈值，不做全词表排序；DEEPINFER_SAMPLER_FORCE_TOPK=4096 时只在前 4096 个里采（用 DeepSelect 做大词表 top-k）。

结构化输出的流水

  1. SamplingParams(so_args={"schema_type": "json"|"regex"|"ebnf", "schema": ...})。
  2. 请求先进线程池用 xgrammar 编译成语法自动机（超时 20 s），编译完才入调度队列，不阻塞引擎主循环。so_matcher_builder.py:58
  3. 每步在 CPU 上推进自动机、填「哪些 token 合法」的 bitmask，与 GPU forward 重叠；TileLang kernel 把非法位置的 logits 置为 −∞。
  4. 和投机解码配合：逐个把草稿喂给自动机，为每个验证位置生成对应的 mask，遇到第一个非法草稿就停，最后按实际接受数回滚（max_rollback_tokens = nextn + 2）。非法草稿在被 mask 的目标分布里概率为 0，自然会被拒绝。sampler.py:361

并行：DP / EP / CP / EPLB

直觉一张卡装不下、也跑不快整个模型。拆分方式决定了每张卡要读多少权重、存多少 KV、每层要通信几次。目标是第 05 节的杠杆 ④：每卡读的权重尽量少，同时通信尽量少。
vLLM稠密模型默认 TP（单机内把每个矩阵切开）；MoE 可开 DP 注意力 + EP，all-to-all 后端可选 DeepEP 等，EPLB 可选。
DeepInfer不用 TP：注意力纯 DP，MoE 纯 EP；decode 用 64–128 卡的宽 EP；长 prompt 用 zigzag CP；EPLB 复制热点专家。

EPLB：热点专家复制

直觉：路由是模型自己学的，总有些专家特别热门。EP 下持有热门专家的卡每步收到的 token 最多，全组都要等它。解决办法是给热门专家多放几份副本，分摊到不同卡上。

  1. MoE dispatch 时顺带统计每个专家收到的 token 数，存进环形窗口。eplb/__init__.py:113
  2. 每隔 DEEPINFER_EXPERT_REARRANGEMENT_STEP_INTERVAL 步（引擎默认 0 = 关；示例脚本设 30），EP 组 all-reduce 窗口计数。
  3. 策略：贪心把最热的逻辑专家复制到冗余槽位，再把物理槽位分到各卡，最小化窗口内各步的峰值负载。policy.py:73
  4. 单机经 IPC / symm_mem 搬权重，跨机走批量 P2P；gate 通过 logical_to_physical_map 路由到新位置。

vLLM 的 EPLB 机制相同（--enable-eplb，窗口 1000 步、每 3000 步重排、冗余专家默认 0）。DeepInfer 文档给出的生产参数：prefill 每卡 4 个冗余、100 步窗口、1000 步重排；decode 每卡 1 个冗余、1000 步窗口、10000 步重排，实测最慢 rank / 平均 ≈ 1.05–1.09。

默认值的坑：冗余专家数 DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS 在引擎里默认是 0（只向上取整到能被 ep_size 整除），README 说的 32 是 examples/_config.py 设置的。自己写调用代码时要手动设。

自测题

1. 为什么 decode 阶段把 batch 从 1 加到 64，每步耗时几乎不变？

decode 每步要把全部权重从显存读一遍，这个时间和 batch 大小无关；而 64 个 token 的计算量远没到 GPU 算力上限。所以耗时由「读权重」决定，batch 变大只是让同一次读取服务更多 token。可以在第 05 节的计算器里验证。

2. PagedAttention 解决了什么问题？DeepInfer 的块大小和 vLLM 有什么不同？

解决按最大长度连续预留导致的显存浪费和碎片，并顺带支持前缀共享与抢占。vLLM 默认 16 token 一块，DeepInfer 是 128 token 一块（代码里写死，见 model_metadata_utils.py:134；文档里 KV 落盘、SWA 存储也都以 128 token 为粒度）。

3. 为什么 NORMAL 引擎不像 vLLM 那样把 prefill 和 decode 混在一个 batch 里？

DP rank 之间在 MoE 层做 all-to-all，同一步所有 rank 的计算量要接近，否则都等最慢的；纯 decode 步形状稳定，可以整图捕获 CUDA Graph；线上本来就是 PD 分离部署。所以每步通过 DP all-reduce 投票选一种（scheduler.hpp:275）。

4. ZOS 下，第 N+1 步调度时 CPU 不知道第 N 步接受了几个草稿，KV 长度怎么算对？

CPU 先按上限准备，prepare_zos_inputs 给出两步 batch 的 remap，然后 GPU 上的 compute_seqlens_k_zos 用上一步的 num_accepted_tokens_gpu 修正 seqlen_k，变长验证时再用置信度修正 seqlen_q 并异步拷回 CPU 给采样用。

5. 置信度头估错了会让输出分布变吗？

不会。它只决定验证多少个草稿；接受与否由 min(1, p/q) 拒绝采样决定，输出分布与不投机一致。估错只影响吞吐。

6. 为什么 DeepSeek 的模型不用张量并行做注意力？

MLA 只有 1 个 KV 头（512 维 latent），TP 无法按头切分，每张卡都要存一整份 KV，显存浪费 TP 倍；每层还多两次 all-reduce。DP 注意力让每卡只存自己请求的 KV，通信只留在 MoE 层。

7. layer 27 的压缩 KV 从哪来？它的 SWA KV 呢？

压缩 KV 用 layer 20 的（kv_source_layer_ids 中不晚于 27 的最大值）；indexer 模块用 layer 24 的；SWA KV 是 layer 27 自己算的。在第 11 节点 layer 27 可以核对。

8. 开 cp=8 能让单卡存下更长的上下文吗？

从代码看不能。K/V 在 CP 组内 all-gather 后每个 rank 都写完整序列的 KV，CP 摊的是 prefill 计算和激活显存。

9. 为什么 YoCo 截断保留 140 个 token，而不是 128？

decode 时最多会回退 nextn+1 个未接受的位置，SWA 窗口需要覆盖 128 + 最大回溯（默认 6），所以要求 KEEP_TOKENS ≥ 窗口 + DEEPINFER_MAX_BACKTRACKING_TOKENS，README 取 140。

代码与文档不一致处

  • scheduler.hpp:557 注释说抢占输出最短的请求，实现先抢占输出最长的（第 09 节）。
  • hugging_face/config.py:159 的 docstring 说 layer 20「属于 prefill 侧」，而 v4_modules/yoco.py:19 把 layer 20 算作第一个 consumer；以后者为准。
  • README 写 balanced CP 是特性，部署文档写生产暂不用 CP：前者是能力，后者是生产配置。
  • 冗余专家默认值：引擎 0，示例与 README 32。
